# 마이팀 제품 기획

> 이 문서는 2026-11-17 기준으로 합의한 최신 제품 방향을 기록한다. 이 문서의 결정과 충돌하는 과거 논의(선수별 등번호 로그인, 선수 개인 계정 연결을 전제로 한 운영, 별도 스타디움 크래프트 게임)는 현재 방향에서 제외한다. 미정 항목은 결정으로 간주하지 않는다.

## 1. 제품 방향

- **제품 정의:** 아마추어 축구팀 운영을 게임처럼 즐기도록 돕는 웹 기반 관리 솔루션
- **주요 고객:** 팀을 위해 시간과 비용을 쓰는 감독·총무 등 팀 운영자
- **핵심 가치:** 팀 관리 부담을 줄이고, 전술·선수단·경기 운영 과정을 재미있고 보람 있게 만든다.
- **차별점:** 실제 팀 운영 기능을 클럽 공간과 축구팀 콘텐츠로 표현하고, 운영 성과와 팀 정체성을 꾸미기 요소로 보여준다.
- **게임 범위:** 별도의 축구 게임을 만드는 것이 아니다. 운영 기능을 게임 감성의 공간·화면·아이템으로 표현한다.
- **팀원 참여:** 운영자가 혼자 사용해도 제품의 핵심 가치는 성립한다. 팀원 참여와 계정 생성은 필수가 아니다. 운영자가 공유하고 싶을 때 팀원용 조회 화면을 제공한다.

## 2. 플랫폼과 화면 원칙

- 웹을 먼저 개발한다. 별도 네이티브 앱이나 데스크톱 앱부터 만들지 않는다.
- **운영자 화면:** PC를 주 화면으로 설계한다. 넓은 작업 공간에서 선수단·전술·일정 등 여러 작업을 편하게 관리한다.
- 운영자용 웹은 태블릿과 모바일에서도 주요 작업을 할 수 있도록 반응형으로 지원한다. 모바일은 출석·검색·간단한 등록과 수정 등 빠른 관리에 집중한다.
- **팀원용 화면:** 운영자 화면과 별도의 간소화된 조회 경험을 제공한다. 초대 링크로 팀 대시보드, 공개된 선수 기록, 운영자가 공유한 전술을 확인한다. 팀원은 선수나 팀 데이터를 수정하지 않는다.
- 향후 웹뷰 또는 데스크톱 컨테이너 적용을 고려하되, 1차 개발은 웹에서 완결한다.
- 공간의 분위기는 탐색과 소속감을 돕고, 등록·검색·저장 등 자주 쓰는 작업은 빠른 메뉴와 명확한 레이아웃으로 제공한다. 게임 요소가 기능의 가독성이나 접근성을 방해하지 않도록 한다.

## 3. 제품 공간과 기능 구성

각 공간은 장식 배경에 그치지 않고 실제 운영 기능으로 연결한다. 아래 공간은 정보 구조의 방향이며, 모든 기능을 첫 버전에 구현한다는 뜻은 아니다.

### 3.1 클럽하우스

팀의 메인 로비이자 각 시설로 이동하는 허브다. 아이소메트릭 공간으로 표현하며, 메인 화면에서 주요 시설·기능 버튼을 눌러 바로 이동할 수 있게 한다. 공간을 둘러보는 조작을 필수로 요구하지 않는다.

- 팀 로비에서 팀 정보와 주요 현황을 확인한다.
- 익명 게시판과 명예의 전당을 둔다. 명예의 전당에는 시즌 레코드, 트로피, 최우수 선수 등의 기록을 포함하는 방향이다.
- 클럽하우스의 하위 공간으로 **미팅룸**을 둔다. 미팅룸은 별도 상위 시설이 아니며, 전술 보드와 라인업 구성을 담당한다.
- 꾸미기 아이템은 공간과 기능 오브젝트를 바꾸는 용도로 검토한다.

### 3.2 스타디움

팀의 홈구장 공간이다. 구단이 홈구장 이름을 정하고 경기 운영 정보를 모아본다.

- 홈구장 이름과 기본 정보를 설정한다.
- 경기 일정 캘린더와 경기별 정보를 관리한다.
- 경기별 라인업을 자동 구성한다.
- 경기 라인업은 클럽하우스 내부 미팅룸의 전술 보드와 연결한다. 경기에서 사용할 선수·전술 정보를 이어서 구성할 수 있어야 한다.

### 3.3 전력분석센터

선수단을 관리하고 전력을 평가·분석하는 시설이다.

- 선수 등록, 정보 수정, 삭제와 검색·필터
- 선수 스탯 평가와 분석, 히든 스탯 및 팀 밸런스 분석
- 선수단 데이터는 스타디움의 경기별 라인업 및 클럽하우스 미팅룸의 전술 구성에서 활용한다.

### 3.4 트레이닝센터

훈련 계획과 기록을 만들고 팀에 공유하는 시설이다.

- 훈련 기획, 대상 선수·목적·설명 관리, 훈련 일지 공유
- 세부 전술 훈련은 전술 보드 애니메이션과 설명을 생성하는 방향
- 선수단 정보와 전술 데이터 등 필요한 기능을 다른 시설과 연결한다.

### 3.5 사무국 기능

사무국은 기능 묶음으로 두며, 세부 공간과 화면 배치는 후속 설계에서 확정한다.

- **단장실:** 운영자 마이페이지와 계정 설정
- **회계팀:** 포인트 지급, 예산, 목적별 회비 관리
- **장비팀:** 축구공·카메라·유니폼·축구화·생수 등 장비 품목 관리
- 회계·결제와 포인트 기능은 정책과 재원 계획을 정한 뒤 단계적으로 구현한다.

### 3.6 시설 간 연결과 바로가기

주요 시설은 각각 메인 화면에서 직접 열 수 있는 바로가기를 제공한다. 메뉴를 시설 구조에 맞춰 보이되, 데이터와 작업 흐름은 관련 시설끼리 이어준다. 예를 들어 전력분석센터의 선수·스탯 정보는 미팅룸 전술 구성과 스타디움 경기별 라인업에서 재사용하고, 스타디움에서 선택한 경기는 미팅룸의 전술 보드 작업으로 이어질 수 있다. 시설 간 연결은 중복 입력을 줄이고 작업 맥락을 유지하기 위한 것으로, 각 기능의 소속 공간을 바꾸지는 않는다.

## 4. 일반적인 팀 운영 기능 후보

기획 후보 목록이며 우선순위에 따라 단계적으로 판단한다.

- 메인 대시보드와 팀 정보
- 경기·훈련 일정
- 전술 보드와 팀원 관리
- 용병 모집·참석 관리
- 경기 기록과 명예의 전당
- 갤러리
- 장비 및 회비 관리
- 선수 프로필과 평가
- 공지, 댓글, 커뮤니티, 단체 소통

채팅·커뮤니티는 알림, 운영 정책, 지속적인 참여가 필요한 별도 범위다. 초기에는 공지와 링크 공유 등 목적이 분명한 기능부터 검토한다.

## 5. 선수·로그인·초대 정책

- 감독·총무가 선수 명단을 만들고 관리한다.
- 팀원에게 선수별 계정을 만들거나 등번호로 로그인하도록 요구하지 않는다.
- 팀원은 감독이 공유한 초대 링크 또는 초대 코드로 조회 화면에 들어온다.
- 팀원 화면은 팀 현황, 허용된 선수 기록, 공유 전술 등 조회 콘텐츠만 제공한다.
- 선수 관리와 평가, 전술 수정, 삭제 권한은 운영자에게 둔다.
- 초대 코드는 운영자가 재발급할 수 있다. 재발급 후 이전 코드로 새 입장은 차단한다.
- 팀원 계정 도입은 초기 제품의 전제 조건이 아니다. 필요성이 확인되면 후속으로 검토한다.

## 6. 전술 보드 및 운영 데이터 기준

전술 보드는 제품의 핵심 실용 기능이다. 게임형 표현보다 배치의 정확성, 결과 설명 가능성, 수동 조정의 편의성을 우선한다.

- 경기 참석 선수, 쿼터 수, 최소 출전, 포메이션을 바탕으로 라인업을 구성한다.
- 출전 횟수 균형, 선수 선호 포지션, 대체 가능한 유사 포지션을 고려한다.
- 골키퍼는 필드 포메이션 판정에서 제외한다.
- 대회 연령·포지션·평가 스탯 등 조건별 스쿼드 구성은 기준을 사용자가 확인할 수 있어야 한다.
- 수동으로 드래그해 바꾼 배치와 표시 포메이션은 일관되게 관리한다.
- 저장 전술은 팀 데이터로 보관하고, 운영자가 공유한 전술만 팀원 조회 화면에 노출한다.
- 자동 추천이 확정적인 평가처럼 보이지 않도록 사용 기준과 한계를 표시한다.

## 7. 아바타·테마·아이템

- 선수 아바타와 액세서리로 선수단과 전술 화면에 개성을 더한다.
- 클럽하우스, 미팅룸, 사무국, 선수단, 라커룸, 스타디움·연습구장 등의 테마와 장식 아이템을 검토한다.
- 구단 색상 및 공간 테마를 선택하는 기능을 제공할 수 있다.
- 꾸미기 요소는 실제 운영 기능과 연결된 보상·표현 수단으로 설계한다. 별도 게임 진행을 강제하지 않는다.
- 무료로 제공할 기본 테마와 구매·획득 가능한 아이템의 구성은 추후 기획한다.
- 도트 배경과 캐릭터 모션은 시각 콘셉트 후보이며, 기본 정보와 조작을 가리지 않도록 한다.

## 8. 수익 모델 가설

수익화는 기능과 반복 사용을 먼저 검증한 뒤 실험한다. 현재는 가설이며 확정된 사업 모델이 아니다.

### 8.1 아이템 및 기능 상품

- 꾸미기 아이템은 팀의 정체성과 공간을 표현하는 구매·획득 요소 후보이며, 주요 수익 모델이 될 가능성을 검토한다.
- 고급 전술 분석, 시뮬레이션, 추가 관리 도구, 가상 직원은 유료 기능 후보로 검토한다.
- 무료·유료 기능 경계는 기본 운영의 신뢰성, 실제 지불 의사, 팀 단위 구매 방식을 살펴본 후 결정한다.
- 유료 직원은 작업을 돕는 분석 도구를 제품 안에서 표현하는 방식이다. 단순 장식인지 실질 기능인지 명확히 구분한다.

### 8.2 포인트와 보상 가설

- 포인트는 운영자가 충전하고 경기 MVP, 참석, 전술 수행, 활동 기여 등의 이유로 선수에게 지급하는 방향을 이전에 논의했다.
- 누적 포인트 랭킹과 시즌 티어, 연말 우수 선수 보상, 꾸미기 아이템 이용이 후보 용도다.
- 과거 예시로 운영자가 5만 원을 충전하고, 그 재원 안에서 3만 원 상당 상품을 우수 선수에게 제공하는 구조를 논의했다. 실제 비용·수수료·예산·운영 방침은 미정이다.
- 포인트 충전·지급과 실물 상품 보상은 핵심 제품 기능이 완성되고 사용자 반응을 확인한 뒤 검증한다. 결제 기능은 초기 단계에서 연동 준비만 할지 여부도 별도 결정한다.
- 현금성 가치, 환불, 만료, 보상 재원, 시즌 정산과 관련된 정책은 출시 전 별도로 확정한다.

## 9. 사용자 가설과 검증

- 전체 대중보다 축구팀을 실제로 운영하는 감독·총무라는 제한된 사용자층에 집중한다.
- 사용자가 많지 않더라도 팀 운영에 높은 관심과 반복 사용을 보일 수 있다는 가설을 검증한다.
- 감독이 팀을 위해 상당한 시간과 개인 비용을 들이는 행동은 구매 가능성을 시사하지만, 결제 의사를 보장하지 않는다.
- 우선 소수의 팀 운영자가 시즌 준비와 실제 경기 운영에 반복 사용하도록 하고 다음을 확인한다.
  - 전술 구성의 정확성과 신뢰도
  - 경기 준비에 드는 시간과 운영 부담의 감소
  - 선수 평가·일정·훈련 기록의 반복 사용
  - 운영자가 팀 현황과 전술을 공유하려는 정도
  - 공간 꾸미기가 재방문과 만족도에 주는 영향
  - 본인 또는 팀 예산으로 지불할 의사가 있는 기능과 아이템

## 10. 구현 순서 제안

1. 제품 구조와 PC 우선 웹 레이아웃을 설계한다. 클럽하우스와 공간 내비게이션을 기준으로 한다.
2. 기존 프로젝트의 인증, API, 팀·선수 데이터, 평가, 전술 로직을 검토해 재사용한다. 화면 구조는 새 컨셉에 맞춰 점진적으로 재구성한다.
3. 클럽하우스 로비와 바로가기 구조를 기준으로 전력분석센터, 미팅룸, 스타디움의 핵심 운영 흐름을 우선 구현한다.
4. 운영자용 모바일 반응형 관리와 팀원용 간소화 조회 화면을 분리해 다듬는다.
5. 일정·훈련·경기 기록 등 운영 기능을 사용자 피드백에 따라 확장한다.
6. 공간 테마, 아바타, 아이템의 획득·구매 방식을 검증한다.
7. 사용성과 수요가 확인되면 포인트 및 결제를 단계적으로 검토한다.

별도 게임을 만들거나 프로젝트 전체를 즉시 폐기하는 대신, 새 화면 구조를 만들고 검증된 핵심 로직과 API를 재사용한다. 이전 화면과 데이터는 새 구조가 충분히 기능을 제공하는지 확인한 뒤 정리한다.
